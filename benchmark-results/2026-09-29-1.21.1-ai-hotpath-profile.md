# UMCE Fabric 1.21.1 hot-path profile: entity AI and suffocation checks

Captured: 2026-09-29 UTC. These are local Spark Java sampling profiles, not performance comparisons. Each run used a 10-second warm-up followed by 30 seconds of sampling. The profiling run used the non-passive diagnostics adapter and no gameplay patch was enabled. Spark could not use async-profiler on this Windows host, so it used its Java sampling engine; treat the inclusive sample weights as directional.

## Workloads

- 500 villagers; profile: [raw Spark profile](2026-09-29-1.21.1-ai-profile-villagers-500.sparkprofile)
- 2,000 pigs and 500 villagers; profile: [raw Spark profile](2026-09-29-1.21.1-ai-profile-mix-2000-pigs-500-villagers.sparkprofile)

## Mixed workload hot stacks

Samples below are inclusive weights beneath `MinecraftServer.runServer` (30,096 total samples); methods on the same stack are not additive.

|---|---:|---|

| `EntityNavigation.findPathTo` | 3,900 | Pathfinding |

The `Stream.anyMatch` stack was traced to `Entity.isInsideWall()` from `LivingEntity.tickMovement`. Bytecode and Yarn 1.21.1 mappings confirm that `BlockPos.stream(Box)` floors all six box edges inclusively and that its iterator already reuses one `BlockPos.Mutable`. The optimization candidate therefore removes Stream pipeline/iterator setup and computes the box VoxelShape once; it does not claim to eliminate one BlockPos allocation per voxel.

## Villager-only profile

The 500-villager run showed `VillagerEntity.tick` (8,396 inclusive samples), `MobEntity.tickNewAi` (6,344), `Brain.tick` (6,144), and `ServerChunkManager.tick` (5,328) near the top. This supports prioritizing villager/AI profiling, but identifies no safe standalone AI rewrite yet.

## Limits

Sampling weights are not method timings, allocations, GC totals, MSPT, or proof of a speedup. Unknown mod callbacks are not parallelized. Next step is an isolated three-condition screening against the exact same workload and passive UMCE.
